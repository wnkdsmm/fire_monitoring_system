4.1 Подготовка среды разработки
4.1.1 Обоснование выбора программной платформы
Разработка сервиса интеллектуального анализа данных о пожарах предполагает решение нескольких технически разнородных задач: загрузку и предобработку табличных данных из ведомственных форм отчётности, вычисление статистических и машинно-обучающих моделей, формирование интерактивных визуализаций и обеспечение доступа к результатам через веб-браузер без установки дополнительного программного обеспечения на стороне пользователя. Совокупность этих требований определила выбор компонентов программной платформы.
Центральным компонентом является язык программирования Python версии 3.11. В задачах анализа данных Python выполняет роль связующего слоя между библиотеками обработки данных, слоем хранения и веб-интерфейсом. Версия 3.11 выбрана как актуальный стабильный релиз: в ней исправлены известные ошибки предыдущих ветвей и обеспечена совместимость со всеми используемыми в проекте сторонними пакетами.
Веб-часть сервиса построена на основе фреймворка FastAPI. FastAPI реализует интерфейс ASGI (Asynchronous Server Gateway Interface), что позволяет выполнять несколько HTTP-запросов конкурентно в рамках одного процесса. Это существенно для данного приложения: часть операций (обучение моделей, кластеризация, прогнозирование) занимает от нескольких секунд до нескольких десятков секунд. При синхронной модели выполнения такие операции блокировали бы обработку других запросов. FastAPI предоставляет встроенный механизм фоновых задач (BackgroundTasks), через который длительные вычисления запускаются асинхронно, а клиент опрашивает их статус отдельными запросами.
В качестве системы управления базами данных используется PostgreSQL версии 15. Реляционная СУБД выбрана потому, что исходные данные о пожарах представляют собой структурированные таблицы с фиксированными атрибутами (дата, место, вид объекта, последствия). Для таких данных реляционная модель обеспечивает целостность, возможность выполнения агрегирующих SQL-запросов (GROUP BY по периодам и районам), а также индексирование по часто используемым полям. PostgreSQL 15 поддерживает полный набор необходимых функций: оконные функции для вычисления скользящих агрегатов, хранение JSON-атрибутов при необходимости, кириллические локали для корректной сортировки и сравнения текстовых полей.
Кэширующий слой реализован на основе Redis версии 7. Redis представляет собой хранилище данных в оперативной памяти с поддержкой структур данных (строки, хэши, списки) и встроенным механизмом автоматического удаления записей по истечении времени жизни (TTL). В данном приложении Redis применяется для сохранения результатов аналитических вычислений между запросами: повторное обращение к дашборду или странице прогнозирования не требует повторного выполнения запросов к PostgreSQL и пересчёта агрегатов — результат извлекается из кэша до истечения его времени жизни.
Целевые операционные системы — Microsoft Windows 11 и Ubuntu 22.04 LTS. Поддержка двух платформ обусловлена требованиями эксплуатации: рабочие места сотрудников противопожарной службы, как правило, работают под Windows, тогда как серверное развёртывание выполняется на Linux. Для Windows предусмотрен VBS-сценарий автозапуска и BAT-сценарий установки зависимостей; для Ubuntu — конфигурация systemd-сервиса.
4.1.2 Состав зависимостей проекта
Зависимости проекта зафиксированы в файле requirements.txt. Каждая библиотека выполняет конкретную функцию в рамках архитектуры сервиса; ниже приведён состав файла и назначение каждого пакета.
fastapi>=0.115
uvicorn>=0.30
jinja2>=3.1
python-multipart>=0.0.9
SQLAlchemy>=2.0
psycopg2-binary>=2.9
numpy>=1.26
pandas>=2.2
plotly>=5.24
scikit-learn>=1.5
statsmodels>=0.14
joblib>=1.4
openpyxl>=3.1
xlrd>=2.0.1
natasha>=1.6
Пакет fastapi реализует маршрутизацию HTTP-запросов, декларативную валидацию входных параметров на основе Pydantic-моделей и сериализацию ответов в формат JSON. Пакет uvicorn является ASGI-сервером: он принимает входящие TCP-соединения и передаёт их в асинхронный обработчик приложения. Именно uvicorn запускается в командной строке при старте сервиса и управляет пулом рабочих процессов в производственном режиме.
Библиотека jinja2 обеспечивает серверный рендеринг HTML-страниц на основе шаблонов. Сервис использует серверный рендеринг, а не одностраничное приложение (SPA), поскольку значительная часть данных формируется на стороне сервера (агрегаты из PostgreSQL, результаты моделей) и не требует отдельного API-слоя для первоначальной загрузки страницы. Пакет python-multipart необходим для разбора тела HTTP-запросов типа multipart/form-data — этот формат используется браузером при отправке файлов через форму загрузки.
SQLAlchemy версии 2.0 выполняет две функции: управление пулом соединений с PostgreSQL и построение SQL-запросов через объектную модель. В данном проекте SQLAlchemy используется преимущественно в режиме Core (прямые SQL-выражения), а не ORM, поскольку аналитические запросы содержат сложные агрегации и оконные функции, которые удобнее выражать непосредственно на SQL. Пакет psycopg2-binary является драйвером, реализующим протокол взаимодействия с PostgreSQL на уровне сокетов; SQLAlchemy использует его через абстракцию DBAPI.
Библиотека pandas предназначена для работы с табличными данными в памяти: загрузки файлов, фильтрации строк, группировки, вычисления производных признаков. В данном проекте pandas применяется на этапе ETL-конвейера при импорте Excel-файлов и при подготовке обучающих выборок для моделей прогнозирования — в частности, для формирования лаговых признаков (значения за предшествующие 1, 7 и 14 суток) и скользящих средних. Библиотека numpy обеспечивает векторные вычисления, на которых строится pandas и scikit-learn.
Библиотека plotly используется для построения интерактивных диаграмм. Plotly генерирует описание графика в формате JSON, который передаётся в браузер и отображается клиентской библиотекой Plotly.js без дополнительных серверных запросов. Это позволяет реализовать масштабирование, фильтрацию по оси времени и всплывающие подсказки без перезагрузки страницы.
Пакет scikit-learn предоставляет реализации алгоритмов машинного обучения, применяемых в трёх подсистемах сервиса. В подсистеме прогнозирования числа пожаров используются логистическая регрессия (бинарная классификация: будет ли пожар в заданный день) и регрессия Пуассона (оценка ожидаемого числа событий). В подсистеме кластеризации применяется алгоритм k-средних для разбиения территорий на группы по совокупности пожарных показателей, а также коэффициент силуэта для оценки качества полученного разбиения. Библиотека statsmodels используется для построения отрицательной биномиальной регрессии — в случаях, когда данные демонстрируют сверхдисперсию, которую модель Пуассона не учитывает. Пакет joblib обеспечивает параллельное выполнение вычислений при обучении моделей на нескольких ядрах.
Библиотеки openpyxl и xlrd обеспечивают чтение файлов в форматах .xlsx и .xls соответственно. Необходимость поддержки обоих форматов обусловлена тем, что ведомственные формы пожарной статистики поставляются как в новом формате Office Open XML (.xlsx), так и в устаревшем бинарном формате (.xls), используемом в более ранних версиях Excel. Библиотека natasha применяется для нормализации топонимов на русском языке: названия населённых пунктов и административных образований в исходных файлах нередко записаны непоследовательно (различные падежи, сокращения), что препятствует корректному сопоставлению записей при агрегации по территориям.
4.1.3 Настройка СУБД PostgreSQL
PostgreSQL устанавливается на сервере (или локальной машине разработчика) штатным способом для соответствующей операционной системы. После установки создаётся отдельная база данных fires, изолированная от системных и прочих пользовательских баз. Создание выделенной базы данных исключает пересечение пространств имён таблиц и позволяет применять политики резервного копирования и восстановления независимо от других баз на том же сервере.
Создание базы данных выполняется от имени суперпользователя через утилиту psql:
CREATE DATABASE fires
WITH OWNER = postgres
ENCODING = 'UTF8'
LC_COLLATE = 'ru_RU.UTF-8'
LC_CTYPE = 'ru_RU.UTF-8'
TEMPLATE = template0;
Параметры ENCODING, LC_COLLATE и LC_CTYPE задают кодировку и локаль. Кодировка UTF-8 необходима, поскольку исходные данные содержат кириллические символы. Локаль ru_RU.UTF-8 определяет правила сравнения и сортировки строк в соответствии с русским языком: при выборке с сортировкой по наименованию района или населённого пункта строки будут упорядочены по русскому алфавиту, а не по кодовым точкам Unicode. Использование template0 вместо template1 обязательно при указании нестандартной локали — template1 уже инициализирован с локалью системы и не допускает её переопределения.
Параметры подключения к базе данных хранятся в файле .env в корневом каталоге проекта и не включаются в систему контроля версий:
DATABASE_URL=postgresql://postgres:PASSWORD@localhost:5432/DATABASE
APP_HOST=127.0.0.1
APP_PORT=8000
Строка подключения DATABASE_URL формируется по схеме postgresql://пользователь:пароль@хост:порт/имя_базы. Она передаётся в SQLAlchemy при инициализации движка. Вынесение параметров подключения в переменные окружения отделяет конфигурацию среды от кода приложения: при переносе на другой сервер достаточно изменить .env без правки исходных файлов.
Инициализация движка базы данных выполняется в модуле config/db.py:
from sqlalchemy import create_engine, text
from dotenv import load_dotenv
import os
load_dotenv()
DATABASE_URL = os.environ["DATABASE_URL"]
engine = create_engine(
DATABASE_URL,
pool_pre_ping=True,
pool_size=5,
max_overflow=10,
)
def check_connection() -> bool:
with engine.connect() as conn:
conn.execute(text("SELECT 1"))
return True
Параметр pool_pre_ping=True включает механизм проверки живости соединения перед его использованием из пула: перед выполнением запроса к базе данных SQLAlchemy отправляет тестовый запрос SELECT 1. Если соединение разорвано (например, по таймауту простоя), оно прозрачно пересоздаётся без возврата ошибки приложению. Параметр pool_size=5 задаёт размер постоянного пула соединений; max_overflow=10 разрешает создание до десяти дополнительных соединений при одновременной обработке большого числа запросов.
Функция check_connection() вызывается при запуске приложения в обработчике события lifespan модуля app/main.py. Цель вызова — убедиться в доступности базы данных до начала обработки пользовательских запросов и зафиксировать ошибку конфигурации на этапе запуска, а не в момент первого обращения к данным.
На начальном этапе развёртывания в базу данных загружается дамп fires.dump, содержащий нормализованные данные, импортированные из исходных Excel-файлов пожарной статистики:
pg_restore -U postgres -d fires fires.dump
После восстановления дампа база данных содержит таблицы с нормализованными атрибутами пожаров: датой и временем регистрации, координатами, видом объекта, площадью загорания, числом пострадавших и иными показателями. В дальнейшем пользователь может загружать дополнительные файлы через веб-интерфейс — они обрабатываются ETL-конвейером и записываются в новые таблицы той же базы данных.
4.1.4 Настройка Redis как уровня кэширования
Ряд операций сервиса является вычислительно затратным: выполнение агрегирующих SQL-запросов по большим таблицам, построение временных рядов, обучение моделей. Если каждое обращение к аналитической странице повторно выполняет весь цикл вычислений, время отклика будет неприемлемым при интерактивной работе. Для устранения этой проблемы в архитектуре предусмотрен кэширующий слой на основе Redis.
Redis хранит данные в оперативной памяти в виде пар ключ–значение. Каждая запись снабжается временем жизни (TTL — Time To Live): по его истечении запись автоматически удаляется, и следующий запрос инициирует повторное вычисление. Механизм TTL позволяет балансировать между актуальностью данных и скоростью отклика: часто меняющиеся данные хранятся с коротким TTL, редко меняющиеся — с длинным.
В данном проекте применяется дифференцированная TTL-политика в зависимости от типа кэшируемых данных:
— метаданные схемы базы данных (список таблиц, состав столбцов): TTL 60 секунд — обновляются при каждой операции импорта, поэтому короткое время жизни обеспечивает актуальность без заметной задержки;
— результаты дашборда (агрегированные KPI по периодам): TTL 300 секунд — данные изменяются только при добавлении новых записей, которое происходит нечасто;
— результаты прогнозирования и параметры обученных моделей: TTL 1800 секунд — пересчёт занимает значительное время, а входные данные между запросами не изменяются;
— картографические объекты в формате HTML: TTL 3600 секунд — генерация карты является наиболее ресурсоёмкой операцией, а географические данные практически не меняются в течение рабочей сессии.
Адрес Redis-сервера задаётся в файле .env:
REDIS_URL=redis://localhost:6379/0
Логика кэширования сосредоточена в модуле app/cache.py. Каждый аналитический запрос перед обращением к PostgreSQL проверяет наличие актуальной записи в Redis. При наличии записи результат возвращается немедленно. При отсутствии — выполняется полный цикл вычислений, результат записывается в Redis с соответствующим TTL. Ключи кэша включают идентификатор таблицы и параметры запроса (период, выбранные метрики), что обеспечивает изоляцию кэшированных результатов для разных наборов данных и настроек.
При операции импорта новых данных вызывается функция invalidate_db_metadata_cache(), которая принудительно удаляет из Redis записи метаданных схемы. Это необходимо, поскольку после создания новой таблицы старый кэш со списком таблиц становится неактуальным, и пользователь должен немедленно увидеть обновлённый список.
Если Redis недоступен при запуске, приложение переходит в режим без кэширования: все запросы выполняются напрямую к PostgreSQL. Это поведение обеспечивает работу сервиса в минимальной конфигурации (без Redis), что допустимо при небольших объёмах данных или в тестовом окружении.

4.2 Разработка хранилища данных и ETL-подсистемы
4.2.1 Общая архитектура хранилища данных
Данные о пожарах поступают в систему из внешних источников в виде файлов табличного формата (XLSX, XLS, CSV), структура которых варьируется в зависимости от источника: разные подразделения МЧС используют собственные бланки с различными наименованиями столбцов, порядком полей и соглашениями об оформлении. Задача хранилища данных состоит в том, чтобы принять разнородные входные файлы, привести их к единой схеме и предоставить аналитическим подсистемам согласованный интерфейс доступа к данным независимо от особенностей конкретного источника.
Для решения этой задачи в базе данных PostgreSQL выделены четыре уровня хранения, каждый из которых соответствует определённому этапу обработки данных. Первый уровень — таблица исходных данных с динамической схемой — хранит записи в том виде, в каком они поступили из файла, без какого-либо преобразования. Второй уровень — таблица карантина quarantine_records — содержит записи, не прошедшие проверку качества, с указанием причины отклонения. Третий уровень — журнальная таблица etl_log — фиксирует метаданные каждой операции загрузки. Четвёртый уровень — таблица cleaned_fires — содержит нормализованные записи с фиксированной схемой и является единственным источником данных для аналитических подсистем.
Такое разделение решает две задачи. Во-первых, исходные данные сохраняются без изменений, что позволяет повторно выполнить обработку при изменении правил нормализации или маппинга. Во-вторых, аналитические запросы всегда обращаются к cleaned_fires, схема которой предсказуема и не зависит от структуры конкретного входного файла.
4.2.2 Схема базы данных
Схема базы данных включает четыре таблицы, связанные между собой по ключу загрузки (import_id), который присваивается каждой операции импорта.
Таблица исходных данных создаётся динамически при каждой загрузке нового файла. Её имя формируется из временной метки и имени файла (например, raw_fires_20240415_report). Столбцы таблицы соответствуют столбцам входного файла и не приводятся к единой схеме. Таблица содержит обязательный столбец import_id (INTEGER) — внешний ключ, связывающий запись с операцией импорта в etl_log, и row_hash (TEXT) — хэш строки для обнаружения дубликатов. Все содержательные поля хранятся как TEXT, поскольку на этапе сырого хранения типы данных не верифицируются.
Таблица quarantine_records хранит записи, отклонённые на этапе валидации. Её структура приведена ниже.
CREATE TABLE quarantine_records (
id             SERIAL PRIMARY KEY,
import_id      INTEGER NOT NULL,
source_table   TEXT    NOT NULL,
source_row     INTEGER NOT NULL,
raw_data       JSONB   NOT NULL,
rejection_code TEXT    NOT NULL,
rejection_desc TEXT,
created_at     TIMESTAMPTZ DEFAULT now()
);
Поле raw_data хранит исходную строку в формате JSON, что позволяет впоследствии проверить содержимое отклонённой записи без обращения к исходному файлу. Поле rejection_code содержит машиночитаемый код причины отклонения (MISSING_DATE, INVALID_COORDS, DUPLICATE и др.); rejection_desc — текстовое пояснение для оператора.
Таблица etl_log является журналом операций импорта. Каждая строка соответствует одной загрузке файла.
CREATE TABLE etl_log (
import_id       SERIAL PRIMARY KEY,

);
Поле mapping_json хранит результат автоматического определения соответствия столбцов входного файла целевой схеме. Это позволяет при необходимости воспроизвести или скорректировать маппинг для повторной обработки. Поле status принимает значения running, completed или failed, что позволяет обнаруживать прерванные операции импорта.
Таблица cleaned_fires содержит нормализованные записи с фиксированной схемой и является единственной таблицей, к которой обращаются аналитические подсистемы.
CREATE TABLE cleaned_fires (

Индексы по полям fire_date, region и district создаются потому, что большинство аналитических запросов выполняет агрегацию именно по этим измерениям. Ограничение UNIQUE (row_hash) исключает повторное добавление идентичной записи при повторной загрузке того же файла. Поля lat и lon имеют тип NUMERIC(9,6), что обеспечивает точность координат до шестого знака после запятой (порядка 0,1 м), достаточную для задач геоаналитики на уровне населённых пунктов.
4.2.3 Загрузка файла и автоматическое определение маппинга столбцов
Входной файл поступает через веб-интерфейс в виде multipart/form-data запроса и сохраняется во временный каталог data/uploads/. Формат файла определяется по расширению: .xlsx и .xls читаются через библиотеки openpyxl и xlrd соответственно посредством функции pandas.read_excel(), файлы .csv — через pandas.read_csv() с автоматическим определением разделителя. В обоих случаях результатом является объект DataFrame, строки которого соответствуют записям о пожарах, а столбцы — полям исходной формы отчётности.
Основная сложность на этапе загрузки состоит в том, что наименования столбцов исходного файла не совпадают с полями целевой таблицы cleaned_fires. Поле с датой пожара может называться «Дата», «Дата пожара», «Дата возгорания», «date_fire» и т. д. Для автоматического сопоставления применяется алгоритм нечёткого сравнения строк на основе библиотеки fuzzywuzzy.
Алгоритм работает следующим образом. Для каждого целевого поля (например, fire_date) определён набор канонических наименований — эталонных вариантов названия столбца. Каждый столбец входного файла сравнивается с каждым каноническим наименованием посредством функции fuzz.token_sort_ratio(), возвращающей степень сходства в диапазоне от 0 до 100. Функция token_sort_ratio применяется вместо простого отношения Левенштейна потому, что она нечувствительна к перестановке слов внутри строки: «дата пожара» и «пожара дата» дадут одинаковый результат.
Если максимальная степень сходства превышает пороговое значение 85 (что соответствует коэффициенту 0,85 по стобалльной шкале fuzzywuzzy), столбец входного файла считается распознанным и сопоставляется с соответствующим целевым полем. Если для одного целевого поля найдено несколько кандидатов, выбирается тот, у которого степень сходства максимальна. Столбцы, не получившие сопоставления, остаются в сырой таблице, но не переносятся в cleaned_fires.
from fuzzywuzzy import fuzz
CANONICAL = {
"fire_date":         ["дата пожара", "дата", "date", "дата возгорания"],
"region":            ["регион", "субъект", "область", "республика", "region"],
"district":          ["район", "муниципальный район", "district"],
"locality":          ["населённый пункт", "нп", "город", "село", "locality"],
"object_type":       ["вид объекта", "объект", "тип объекта", "object_type"],
"fire_cause":        ["причина пожара", "причина", "причина возгорания"],
"lat":               ["широта", "lat", "latitude", "y"],
"lon":               ["долгота", "lon", "longitude", "x"],
"damage_rub":        ["ущерб", "ущерб руб", "материальный ущерб", "damage"],
"injured":           ["пострадало", "травмировано", "ранено", "injured"],
"killed":            ["погибло", "погибших", "killed", "смертей"],
"response_time_min": ["время прибытия", "время реагирования", "response_time"],
}
THRESHOLD = 85
def detect_mapping(columns: list[str]) -> dict[str, str]:
mapping = {}
norm = [c.strip().lower() for c in columns]
for target, variants in CANONICAL.items():
best_score, best_col = 0, None
for col, col_norm in zip(columns, norm):
for v in variants:
score = fuzz.token_sort_ratio(col_norm, v)
if score > best_score:
best_score, best_col = score, col
if best_score >= THRESHOLD:
mapping[best_col] = target
return mapping
Результат маппинга сохраняется в поле mapping_json таблицы etl_log, что позволяет оператору проверить, какие столбцы были распознаны автоматически, и при необходимости скорректировать маппинг вручную через интерфейс управления импортом.
4.2.4 Нормализация текстовых полей и дат
После определения маппинга данные проходят этап нормализации, цель которого — устранить вариативность в написании значений, которая препятствует корректной агрегации. Нормализация выполняется отдельно для текстовых полей (топонимов) и полей дат.
Нормализация топонимов необходима потому, что наименования районов и населённых пунктов в исходных файлах записаны непоследовательно: одно и то же место может встречаться как «Красноярский район», «Красноярск. р-н», «красноярский РАЙОН», «Krasnoyarsky rayon». Если не привести эти варианты к единому виду, агрегация по полю district разобьёт записи об одном районе на несколько групп.
Нормализация выполняется в три шага. На первом шаге строка приводится к нижнему регистру и транслитерируется функцией unidecode.unidecode() из библиотеки unidecode. Транслитерация устраняет проблему смешанного использования кириллицы и латиницы в пределах одного значения. На втором шаге регулярными выражениями удаляются типовые сокращения и служебные слова: «р-н», «район», «обл.», «область», «с.», «д.», «г.», «пгт» и их транслитерированные эквиваленты. На третьем шаге строка приводится к нормальной форме: лишние пробелы удаляются, первая буква каждого слова переводится в верхний регистр. Результирующее значение записывается в соответствующее поле cleaned_fires.
Нормализация дат решает задачу интерпретации различных форматов представления даты пожара. В исходных файлах встречаются следующие форматы: DD.MM.YYYY (наиболее распространённый в российских формах), YYYY-MM-DD (ISO 8601), DD/MM/YYYY, MM/DD/YYYY (в файлах, сформированных англоязычными версиями Excel), а также числовые серийные значения Excel — целое число, представляющее количество дней, прошедших с 1 января 1900 года.
Автоопределение формата выполняется перебором списка форматов посредством datetime.strptime() до первого успешного разбора. Числовые значения распознаются отдельно через функцию pandas.Timestamp.fromordinal(). Если ни один формат не подошёл, значение направляется в карантин с кодом INVALID_DATE. После разбора дата приводится к типу Python datetime.date и сохраняется в поле fire_date типа DATE в PostgreSQL.
Для числовых полей (damage_rub, injured, killed, response_time_min) выполняется приведение типов с обработкой нестандартных значений: строки «нет данных», «н/д», «-», пустые значения интерпретируются как NULL. Отрицательные значения полей injured и killed считаются некорректными и направляются в карантин.
Для полей координат lat и lon дополнительно проверяется диапазон допустимых значений: широта должна находиться в пределах от 41° до 82° с. ш., долгота — от 19° до 190° в. д. (диапазоны охватывают территорию Российской Федерации). Значения за пределами диапазона могут указывать на перепутанные столбцы (широта и долгота записаны в обратном порядке) или на ошибки ввода.
4.2.5 Валидация записей и механизм карантина
Валидация выполняется после нормализации. Каждая запись проверяется на соответствие набору правил; при нарушении хотя бы одного правила запись не поступает в cleaned_fires, а направляется в quarantine_records с соответствующим кодом причины.
Обязательные поля: fire_date и region. Отсутствие даты пожара делает запись непригодной для временного анализа; отсутствие региона — для территориального анализа. Если хотя бы одно из этих полей не удалось извлечь из строки, запись получает код MISSING_REQUIRED.
Проверка координат: если оба поля lat и lon присутствуют, проверяется их принадлежность допустимому диапазону. При нарушении диапазона поля координат обнуляются (устанавливаются в NULL), сама запись при этом не отклоняется — она сохраняется в cleaned_fires без координат, поскольку дата и регион достаточны для большинства аналитических задач. Код предупреждения INVALID_COORDS фиксируется в поле rejection_desc журнала, но запись остаётся в основном потоке.
Обнаружение дубликатов выполняется в два этапа. На первом этапе вычисляется хэш строки (SHA-256 конкатенации значений fire_date, region, district, locality, object_type) и проверяется его наличие в cleaned_fires. Точное совпадение хэша означает, что идентичная запись уже присутствует в базе данных; такая запись получает код DUPLICATE и не добавляется повторно.
На втором этапе выполняется нечёткая проверка на пространственно-временные дубликаты: отбираются записи в cleaned_fires с тем же районом, тем же населённым пунктом и датой в пределах ±1 суток от даты проверяемой записи. Если среди них есть запись с тем же видом объекта, проверяемая запись считается вероятным дубликатом и получает код NEAR_DUPLICATE. Такие записи направляются в карантин для ручной проверки оператором, а не отклоняются автоматически, поскольку на одном объекте теоретически возможно два пожара в течение двух суток.
def is_near_duplicate(conn, row: dict) -> bool:
sql = text("""
SELECT 1 FROM cleaned_fires
WHERE district = :district
AND locality = :locality
AND object_type = :object_type
AND fire_date BETWEEN :date_lo AND :date_hi
LIMIT 1
""")
result = conn.execute(sql, {
"district":    row["district"],
"locality":    row["locality"],
"object_type": row["object_type"],
"date_lo":     row["fire_date"] - timedelta(days=1),
"date_hi":     row["fire_date"] + timedelta(days=1),
})
return result.fetchone() is not None
Все отклонённые записи добавляются в quarantine_records одной транзакцией в конце этапа валидации. Это позволяет оператору просматривать карантин по каждой операции импорта, исправлять данные вручную и повторно запускать обработку для карантинных записей.
4.2.6 Upsert-операция и ведение журнала ETL
Запись нормализованных и прошедших валидацию данных в таблицу cleaned_fires выполняется через механизм upsert (INSERT ... ON CONFLICT DO NOTHING). Использование обычного INSERT без проверки конфликтов привело бы к ошибке нарушения ограничения UNIQUE(row_hash) при повторной загрузке файла. Директива ON CONFLICT DO NOTHING молча пропускает уже существующие записи, не прерывая транзакцию.
Вставка выполняется пакетами (batch insert) по 500 строк за одну транзакцию. Пакетная вставка снижает накладные расходы на управление транзакциями по сравнению с построчной вставкой: для файла из 10 000 строк число транзакций сокращается с 10 000 до 20. Размер пакета выбран как компромисс между потреблением памяти (хранение строк пакета в памяти Python) и числом обращений к базе данных.
Вставка реализована через SQLAlchemy Core с использованием метода connection.execute(insert_statement, rows_list). Такой подход позволяет SQLAlchemy сформировать один SQL-запрос с несколькими строками значений (INSERT INTO ... VALUES (...), (...), ...), что существенно эффективнее последовательного выполнения отдельных запросов.
Параллельно с вставкой данных ведётся обновление записи в etl_log. В начале операции импорта создаётся строка со статусом running и временной меткой started_at. Счётчики rows_total, rows_loaded, rows_quarantine и rows_duplicate обновляются после завершения каждой пакетной вставки. По завершении операции статус устанавливается в completed и заполняется поле finished_at. В случае необработанного исключения статус устанавливается в failed, а текст исключения записывается в поле error_message.
Весь цикл обработки одного файла — от чтения до записи в cleaned_fires и обновления etl_log — выполняется в рамках одной Python-функции run_pipeline(), которая вызывается как фоновое задание FastAPI. Это обеспечивает атомарность на уровне операции импорта: если процесс прерывается на середине, статус в etl_log остаётся running, что позволяет обнаружить незавершённые операции и при необходимости перезапустить их.
4.2.7 Роль таблицы cleaned_fires как единого аналитического источника
Таблица cleaned_fires выполняет функцию единой точки доступа для всех аналитических подсистем сервиса. Ни одна из подсистем — ни прогнозирование, ни кластеризация, ни оценка риска, ни анализ доступности пунктов охраны — не обращается к сырым таблицам или таблице карантина. Такая архитектура отделяет логику обработки данных от логики анализа: изменение правил нормализации или добавление нового источника данных не требует правки аналитического кода.
Фиксированная схема cleaned_fires определяет набор измерений, по которым возможна агрегация: временное измерение (fire_date), территориальное измерение (region, district, locality), атрибутивное измерение (object_type, fire_cause) и координатное измерение (lat, lon). Количественные показатели (damage_rub, injured, killed, response_time_min) доступны для суммирования и усреднения в любом разрезе этих измерений.
Индексы по полям fire_date, region и district обеспечивают приемлемое время выполнения аналитических запросов при объёмах данных, характерных для региональной пожарной статистики (десятки тысяч записей). При существенном росте объёма данных схема допускает партиционирование по полю fire_date (по годам) без изменения запросов аналитических подсистем.
Наличие поля import_id в cleaned_fires обеспечивает прослеживаемость происхождения каждой записи: по значению import_id можно восстановить, из какого файла и в ходе какой операции загрузки была добавлена запись, каков был её исходный вид в сырой таблице и каков был результат маппинга столбцов. Это свойство важно при обнаружении систематических ошибок в данных: если оказывается, что определённый источник поставляет некорректные значения координат или причин пожара, все затронутые записи можно идентифицировать по import_id и скорректировать.
Таким образом, ETL-подсистема обеспечивает преобразование разнородных входных файлов в однородное хранилище с известными структурой и качеством данных. Граница между уровнем хранения (cleaned_fires) и уровнем анализа позволяет развивать аналитические подсистемы независимо от изменений в форматах исходных данных.

4.3.1 Реализация модуля информационной панели
Модуль информационной панели (dashboard) предоставляет агрегированный обзор пожарной обстановки за выбранный период и территорию. Его задача — сформировать набор ключевых показателей и визуализаций по данным таблицы cleaned_fires и вернуть их клиенту в едином JSON-ответе, который Jinja2-шаблон преобразует в HTML-страницу.
Агрегация данных выполняется SQL-запросами через SQLAlchemy Core. Каждый запрос принимает два параметра фильтрации: временной диапазон (date_from, date_to) и регион (region). Если регион не указан, фильтр по нему не применяется и агрегация выполняется по всем регионам. Пример запроса для расчёта KPI-блока:
SELECT
COUNT(*)                        AS total_fires,
COALESCE(SUM(killed),  0)       AS total_killed,
COALESCE(SUM(injured), 0)       AS total_injured,
COALESCE(SUM(damage_rub), 0)    AS total_damage,
COUNT(DISTINCT district)        AS districts_affected
FROM cleaned_fires
WHERE fire_date BETWEEN :date_from AND :date_to
AND (:region IS NULL OR region = :region);
На основе результата этого запроса формируются пять KPI-карточек: общее число пожаров, суммарное число погибших, суммарное число пострадавших, суммарный материальный ущерб и число затронутых районов. COALESCE используется потому, что поля killed, injured и damage_rub допускают NULL — агрегация SUM по столбцу с NULL-значениями возвращает NULL, а не 0, что некорректно для отображения в интерфейсе.
Визуализации формируются тремя отдельными запросами, каждый из которых возвращает данные для одного типа графика.
Первый тип — график динамики — отображает число пожаров по периодам (месяцам или годам в зависимости от длины выбранного диапазона). Запрос группирует записи по усечённой дате (DATE_TRUNC('month', fire_date)) и возвращает пары (период, количество). На основе этих данных Plotly строит линейный график (go.Scatter с mode='lines+markers'). Интерактивность Plotly обеспечивает всплывающие подсказки с точными значениями и возможность масштабирования оси времени без обращения к серверу.
Второй тип — рейтинговый график — показывает топ-10 районов по числу пожаров за период. Запрос группирует записи по полю district, сортирует по убыванию COUNT(*) и ограничивает выборку десятью строками (LIMIT 10). Результат передаётся в go.Bar с горизонтальной ориентацией (orientation='h'), что удобно для отображения длинных наименований районов.
Третий тип — диаграмма распределения — показывает долю пожаров по видам объектов (object_type). Запрос группирует записи по object_type и возвращает количество по каждому виду. Plotly строит круговую диаграмму (go.Pie) с легендой. Виды объектов с долей менее 2% объединяются в категорию «Прочие» на уровне Python до передачи данных в Plotly, чтобы диаграмма оставалась читаемой при большом числе категорий.
Каждый из четырёх запросов (KPI и три графика) выполняется независимо; результаты объединяются в единый словарь и сериализуются в JSON. Чтобы повторные обращения к дашборду с теми же параметрами не вызывали повторного выполнения запросов, результат кэшируется в Redis с ключом вида dashboard:{table}:{date_from}:{date_to}:{region} и временем жизни 300 секунд. Время жизни 300 с выбрано исходя из допустимой задержки актуализации: данные в cleaned_fires обновляются только при явном импорте нового файла, который происходит нечасто. При выполнении импорта соответствующие ключи кэша принудительно инвалидируются через вызов функции invalidate_db_metadata_cache().

4.3.2 Реализация модуля сценарного прогноза
Модуль сценарного прогноза предназначен для оценки ожидаемого числа пожаров на горизонтах 30, 60 и 90 суток в трёх вариантах развития ситуации: оптимистическом, базовом и пессимистическом. Для каждого варианта формируется числовое значение прогноза и доверительный интервал, что позволяет лицу, принимающему решение, оценить не только ожидаемый уровень пожарной активности, но и степень неопределённости прогноза.

import numpy as np
from scipy.stats import poisson
def bootstrap_scenarios(lambda_forecast: np.ndarray,
n_iter: int = 1000) -> dict:
samples = np.stack([
poisson.rvs(mu=lambda_forecast, random_state=i)
for i in range(n_iter)
])                             # shape: (n_iter, horizon)
total = samples.sum(axis=1)   # суммарное число пожаров за горизонт
return {
"optimistic": int(np.percentile(total, 10)),
"base":       int(np.percentile(total, 50)),
"pessimistic":int(np.percentile(total, 90)),
"ci_low":     int(np.percentile(total, 5)),
"ci_high":    int(np.percentile(total, 95)),
}

4.3.3 Реализация модуля машинного обучения
Модуль машинного обучения решает задачу регрессии: по набору признаков, описывающих временной период и территориальный контекст, предсказывается ожидаемое число пожаров в конкретном районе за месяц. В отличие от модуля сценарного прогноза, работающего с агрегированным рядом по всей выборке, данный модуль учитывает территориальную специфику каждого района, что позволяет получать прогнозы на уровне отдельных административных единиц.
Обучающая выборка формируется из таблицы cleaned_fires SQL-запросом, группирующим записи по (DATE_TRUNC('month', fire_date), district, object_type) и вычисляющим COUNT(*) как целевую переменную. Результат загружается в DataFrame и дополняется признаками. Числовые признаки включают: год (year), номер месяца (month), лаговые значения числа пожаров в том же районе за 1 месяц назад (lag₁), 3 месяца назад (lag₃) и 12 месяцев назад (lag₁₂). Категориальные признаки — наименование района (district) и вид объекта (object_type) — преобразуются методом прямого кодирования (One-Hot Encoding) посредством sklearn.preprocessing.OneHotEncoder. OHE применяется, а не порядковое кодирование, поскольку между категориями отсутствует естественный порядок: нет оснований считать, что «жилой дом» ближе к «промышленному объекту», чем к «складу».
Строки, для которых лаговые значения не могут быть вычислены из-за отсутствия данных за предшествующие периоды, исключаются из обучающей выборки. Это приводит к потере первых 12 наблюдений по каждому району, что является стандартной платой за использование лаговых признаков при работе с короткими рядами.
В качестве модели применяется градиентный бустинг над деревьями решений (GradientBoostingRegressor из sklearn.ensemble). Ансамблевый метод выбран потому, что данные сочетают нелинейные зависимости (взаимодействия между сезоном и типом объекта) с выбросами (отдельные месяцы с аномально высоким числом пожаров), для которых линейные модели дают систематические ошибки. Градиентный бустинг строит ансамбль M деревьев, каждое из которых последовательно аппроксимирует псевдоостатки предыдущего шага. Прогноз записывается как:

4.3.4 Реализация модуля кластеризации
Модуль кластеризации решает задачу разбиения административных районов на однородные группы по пожарным характеристикам. Цель разбиения — выявить районы со схожим профилем пожарной активности: интенсивностью, структурой по видам объектов, уровнем последствий. Результат используется при распределении профилактических ресурсов: районы одного кластера предположительно требуют аналогичного набора мер воздействия.
Матрица объектов формируется SQL-запросом к cleaned_fires: каждая строка соответствует одному району, столбцы — агрегированным показателям за выбранный период. Набор признаков включает: общее число пожаров, число погибших, число пострадавших, суммарный материальный ущерб, среднее время реагирования, а также доли пожаров по основным видам объектов (жилой сектор, транспорт, промышленность, прочие). Итоговая матрица имеет размерность n × p, где n — число районов в выборке, p — число признаков.

Преобразование сжимает правостороннюю асимметрию распределения: несколько районов с аномально высоким числом пожаров не будут доминировать в вычислении центроидов кластеров.

где a(i) — среднее расстояние от объекта i до остальных объектов его кластера (мера сплочённости), b(i) — минимальное среднее расстояние от объекта i до объектов ближайшего чужого кластера (мера отделённости). Значение s(i) ∈ [−1, 1]; среднее силуэтное значение S̄(k) = mean{s(i)} вычисляется функцией sklearn.metrics.silhouette_score(). Оптимальным считается k, при котором S̄(k) максимально.
Итоговое k выбирается как наименьшее из двух кандидатов — от метода локтя и от максимума силуэта — при условии, что оба метода указывают на значения в одном диапазоне (±1). Если оценки расходятся более чем на 2, предпочтение отдаётся значению силуэта как формально обоснованному критерию.
Обучение выполняется через KMeans с инициализацией k-means++. Инициализация k-means++ выбирает начальные центроиды последовательно с вероятностью, пропорциональной квадрату расстояния до ближайшего уже выбранного центроида, что снижает чувствительность результата к случайному выбору стартовых точек по сравнению со случайной инициализацией. Параметр n_init=10 задаёт число независимых запусков алгоритма; итоговое решение — то, при котором достигнута наименьшая инерция среди всех запусков.
from sklearn.cluster import KMeans
from sklearn.metrics import silhouette_score
scores = {}
for k in range(2, 16):
km = KMeans(n_clusters=k, init="k-means++",
n_init=10, random_state=42)
labels = km.fit_predict(Z)          # Z — стандартизованная матрица
scores[k] = {
"inertia":   km.inertia_,
"silhouette": silhouette_score(Z, labels),
}
k_best = max(scores, key=lambda k: scores[k]["silhouette"])
model  = KMeans(n_clusters=k_best, init="k-means++",

4.3.5 Реализация модуля анализа проблемных точек
Модуль анализа проблемных точек предназначен для ранжирования населённых пунктов по степени пожарной опасности и формирования приоритетного списка территорий, требующих первоочередного внимания. В отличие от модуля кластеризации, который разбивает районы на группы по сходству профилей, данный модуль вычисляет индивидуальный числовой индекс риска для каждого населённого пункта, позволяя сравнивать их между собой в единой шкале.
На первом этапе из таблицы cleaned_fires формируется агрегированная таблица на уровне населённых пунктов. SQL-запрос группирует записи по полю locality и для каждого пункта вычисляет: число пожаров за период (Nₗ), суммарный материальный ущерб (damage_rub), число погибших и пострадавших, дату последнего зафиксированного пожара (max(fire_date)), а также средние координаты (avg(lat), avg(lon)) для размещения объекта на карте. 4.3.6 Реализация модуля интерактивной карты пожаров
Интерактивная карта пожаров является пространственным компонентом сервиса, отображающим географическое распределение инцидентов, зоны концентрации очагов и приоритетные территории для превентивного вмешательства. Карта формируется как самодостаточный HTML-документ средствами библиотеки Folium, которая генерирует код на основе JavaScript-библиотеки Leaflet.js и не требует постоянного соединения с сервером после первоначальной загрузки. Пользователь получает возможность масштабировать карту, переключать слои и просматривать атрибуты объектов без повторных запросов к серверу.
Карта включает четыре независимых слоя, каждый из которых может быть включён или отключён через элемент управления LayerControl: слой маркеров отдельных пожаров, тепловая карта плотности, слой пространственных кластеров DBSCAN и слой приоритетных зон. Слои формируются последовательно; их совместное отображение даёт аналитику полную картину пространственной структуры пожарной активности.
Исходными данными служат записи таблицы cleaned_fires, имеющие непустые поля lat и lon. Поскольку координаты присутствуют не во всех записях (часть отклоняется на этапе ETL-валидации), перед построением карты выполняется фильтрация: отбираются строки, удовлетворяющие условию lat IS NOT NULL AND lon IS NOT NULL. Для каждой точки вычисляется взвешенная тяжесть sᵢ = log(damage_rub + 1), используемая как весовой коэффициент при построении тепловой карты.

4.4 Разработка веб-интерфейса и API
4.4.1 Архитектура FastAPI-приложения
Серверная часть сервиса построена на фреймворке FastAPI и запускается через ASGI-сервер uvicorn. Интерфейс ASGI (Asynchronous Server Gateway Interface) обеспечивает конкурентную обработку HTTP-запросов в рамках единого event loop без создания отдельного потока на каждое соединение. Это позволяет обслуживать запросы к страницам интерфейса одновременно с выполнением длительных аналитических операций в фоне.
Приложение инициализируется в модуле app/main.py. Жизненный цикл управляется через контекстный менеджер lifespan, который FastAPI вызывает при запуске и остановке процесса. В блоке запуска выполняются три операции: проверка подключения к PostgreSQL через check_connection(), проверка доступности Redis, и прогрев кэша метаданных таблиц. Если хотя бы одна из критических проверок завершается ошибкой, приложение прерывает запуск с диагностическим сообщением, не допуская ситуации, при которой сервис работает с неинициализированными компонентами.
Маршруты разделены на два независимых роутера с разными префиксами и назначениями. Роутер страниц (app/routes/pages.py) обрабатывает GET-запросы к HTML-страницам: он получает данные из аналитических сервисов, передаёт их в Jinja2-шаблон и возвращает клиенту готовый HTML-документ. Роутер API (app/routes/api.py) обрабатывает запросы от клиентского JavaScript: возвращает JSON-ответы с данными для динамического обновления интерфейса и принимает команды запуска фоновых вычислений. Такое разделение позволяет независимо версионировать API и изменять шаблоны страниц без затрагивания контрактов JSON-эндпоинтов.
В качестве middleware подключается CORSMiddleware с ограниченным списком разрешённых источников: в тестовой конфигурации — только localhost, в производственной — только домен, на котором развёрнут сервис. Дополнительно подключается GZipMiddleware для сжатия ответов размером более 1 КБ: это существенно снижает трафик при передаче JSON-данных Plotly, размер которых для сложных диаграмм может достигать нескольких сотен килобайт.
4.4.2 Система фоновых задач и потокобезопасность
Ряд аналитических операций — обучение ML-модели, кластеризация, прогнозирование, импорт файла — занимает от нескольких секунд до минуты. Выполнение таких операций в синхронном обработчике HTTP-запроса заблокировало бы event loop и сделало бы сервис недоступным для других пользователей на время вычислений. Для решения этой проблемы реализована система фоновых задач на основе ThreadPoolExecutor.
Каждая длительная операция запускается парой маршрутов. Первый маршрут (POST /api/{module}-jobs) принимает параметры задачи, регистрирует её в хранилище JobStore, передаёт функцию вычислений в пул потоков и немедленно возвращает клиенту идентификатор задачи (job_id) со статусом running. Второй маршрут (GET /api/{module}-jobs/{job_id}) принимает идентификатор и возвращает текущий статус задачи: running, completed или failed — вместе с результатом при завершении или текстом ошибки при неудаче. Клиентский JavaScript опрашивает второй маршрут с интервалом 2 секунды до получения финального статуса.
Жизненный цикл задачи включает следующие состояния. При создании задача переводится в состояние created и сразу в running. В процессе выполнения функция вычислений периодически дополняет поле logs текстовыми сообщениями о прогрессе, которые клиент может читать при каждом опросе статуса. По завершении задача переводится в completed, результат сохраняется в поле result. При необработанном исключении задача переводится в failed, трассировка ошибки записывается в поле error_message.
Хранилище JobStore реализовано в модуле app/state.py как глобальный объект с внутренним словарём сессий и задач. Поскольку ThreadPoolExecutor выполняет задачи в отдельных потоках, а FastAPI обрабатывает HTTP-запросы в event loop, доступ к общему словарю должен быть защищён от гонок данных. Для этого применяется threading.RLock — реентерабельная блокировка, допускающая повторный захват из одного и того же потока. Каждая операция чтения или записи состояния задачи выполняется внутри блока with self._lock. При возврате результата клиенту выполняется copy.deepcopy(job.result), что исключает возможность модификации кэшированного результата через ссылку, полученную клиентским кодом.
Идентификация сессии пользователя выполняется через HTTP-cookie. При первом обращении к любому маршруту страниц генерируется UUID сессии, который устанавливается в cookie session_id со временем жизни 24 часа. Все задачи, созданные в рамках одной сессии, хранятся в отдельном пространстве имён JobStore. Это обеспечивает изоляцию задач между разными пользователями, работающими с сервисом одновременно, без необходимости реализации полноценной аутентификации.
from concurrent.futures import ThreadPoolExecutor
import threading, copy, uuid
_executor = ThreadPoolExecutor(max_workers=4)
class JobStore:
def __init__(self):
self._lock    = threading.RLock()
self._sessions: dict[str, dict] = {}
def create_job(self, session_id: str, kind: str) -> str:
job_id = str(uuid.uuid4())
with self._lock:
self._sessions.setdefault(session_id, {})[job_id] = {
"kind": kind, "status": "running",
"result": None, "error": None, "logs": [],
}
return job_id
def get_result(self, session_id: str, job_id: str) -> dict:
with self._lock:
job = self._sessions[session_id][job_id]
return {**job, "result": copy.deepcopy(job["result"])}
4.4.3 Многоуровневая система кэширования
В сервисе реализована трёхуровневая система кэширования, каждый уровень которой предназначен для данных с определённым временем жизни и объёмом.
Первый уровень — TTL-кэш на основе Redis — применяется для результатов аналитических запросов к PostgreSQL: агрегатов дашборда, прогнозных рядов, результатов кластеризации и HTML-объектов карт. Структура ключа включает имя модуля, идентификатор таблицы и хэш параметров запроса: dashboard:{table}:{hash(params)}. Время жизни дифференцировано: 60 с для метаданных схемы БД, 300 с для агрегатов дашборда, 1800 с для результатов моделей, 3600 с для карт. При любой операции записи в cleaned_fires (завершении импорта) выполняется принудительная инвалидация ключей с префиксом текущей таблицы через команду Redis SCAN + DEL.
Второй уровень — LRU-кэш в памяти процесса — применяется для вычислительно дешёвых, но часто вызываемых функций: получения списка таблиц, чтения конфигурационных констант, построения строк SQL. Реализован через стандартный декоратор functools.lru_cache(maxsize=128). LRU-кэш уместен здесь потому, что данные, которые он хранит, меняются редко (только при DDL-операциях), а накладные расходы на обращение к Redis для столь частых вызовов были бы избыточны.
Третий уровень — дисковый кэш — используется исключительно для обученных ML-моделей, сохраняемых через joblib.dump() в каталог data/results/. Модель занимает от нескольких мегабайт до десятков мегабайт в зависимости от числа деревьев ансамбля; хранение таких объектов в Redis нецелесообразно. При запросе страницы ML-модуля выполняется проверка: если файл модели существует и его временная метка новее последней операции импорта в etl_log, модель загружается с диска; иначе инициируется повторное обучение.
Защита от мутации кэшированных объектов обеспечивается на двух уровнях. При извлечении объекта из Redis выполняется десериализация (json.loads или pickle.loads), которая по своей природе создаёт новый объект. При возврате объекта из LRU-кэша или JobStore применяется copy.deepcopy(), поскольку functools.lru_cache возвращает ссылку на кэшированный объект, и его модификация в клиентском коде испортила бы кэш для всех последующих вызовов.
4.4.4 Шаблонизация Jinja2 и встраивание визуализаций
HTML-страницы сервиса формируются через механизм наследования шаблонов Jinja2. Базовый шаблон base.html определяет общую структуру документа: подключение Bootstrap 5 (CSS и JS), боковую навигационную панель (sidebar_nav.html), блок-заголовок страницы и расширяемый блок content, который дочерние шаблоны переопределяют. Такая структура исключает дублирование разметки: изменение навигационного меню или подключаемых библиотек требует правки только base.html.
Каждая аналитическая страница — dashboard.html, forecasting.html, ml_model.html, clustering.html, access_points.html — является дочерним шаблоном, расширяющим base.html через директиву {% extends 'base.html' %} и заполняющим блок content собственной разметкой. Передача данных из Python в шаблон выполняется через словарь контекста функции TemplateResponse: числовые KPI передаются напрямую, данные для диаграмм — в виде JSON-строк.
Встраивание интерактивных диаграмм Plotly в страницу выполняется двухэтапно. На стороне Python объект Figure сериализуется в JSON через plotly.io.to_json() и передаётся в шаблон как строковая переменная. В шаблоне JSON-строка помещается в тег <script> как инициализирующие данные, после чего Plotly.js разворачивает диаграмму в назначенном контейнере <div>:
{# в шаблоне Jinja2 #}
<div id="chart-dynamics"></div>
<script>
const figData = {{ chart_dynamics_json | safe }};
Plotly.newPlot("chart-dynamics",
figData.data, figData.layout,
{responsive: true, displayModeBar: false});
</script>
Фильтр | safe отключает экранирование HTML-символов для этой переменной, что необходимо, поскольку JSON-строка содержит угловые скобки и кавычки, которые Jinja2 по умолчанию экранирует. Применение | safe безопасно здесь, поскольку JSON формируется исключительно серверным кодом и не содержит пользовательского ввода.
Для аналитических модулей с длительным временем вычислений (прогнозирование, ML, кластеризация) применяется стратегия отложенной загрузки. Страница первоначально отображается с индикаторами загрузки; клиентский JavaScript отправляет POST-запрос на запуск фоновой задачи, затем опрашивает эндпоинт статуса с интервалом 2 секунды. При получении статуса completed данные диаграмм извлекаются из JSON-ответа и передаются в Plotly.react() для обновления графиков без перезагрузки страницы:
// клиентский JS (упрощённо)
async function pollJob(jobId) {
while (true) {
const res  = await fetch(`/api/forecasting-jobs/${jobId}`);
const data = await res.json();
if (data.status === "completed") {
Plotly.react("chart-forecast",
data.result.chart.data,
data.result.chart.layout);
break;
}
if (data.status === "failed") { showError(data.error); break; }
await new Promise(r => setTimeout(r, 2000));
}
}
4.4.5 Интерактивная карта пожаров в веб-интерфейсе
Страница fire_map.html предоставляет три режима отображения данных, переключаемых через элементы управления без перезагрузки страницы: markers — отдельные маркеры каждого пожара; heatmap — тепловая карта плотности; both — совмещённый режим с обоими слоями одновременно.
Поскольку Folium генерирует HTML-документ с собственной структурой DOM и инициализацией Leaflet.js, встраивание карты напрямую в основную страницу создаёт конфликты между JavaScript-средами. Для изоляции применяется элемент <iframe>: карта загружается как отдельный документ внутри фрейма, не разделяя глобальное пространство имён с основной страницей. Высота iframe задаётся динамически через JavaScript после загрузки карты, исходя из высоты видимой области браузера.
При числе точек пожаров в отфильтрованной выборке более 10 000 применяется принудительное прореживание: из набора случайно отбираются 10 000 записей с сохранением пропорций по районам. Ограничение обусловлено производительностью Leaflet.js: рендеринг более 10 000 маркеров приводит к заметным задержкам отклика карты при масштабировании и перемещении. Для режима heatmap ограничение не применяется, поскольку HeatMap работает с суммарными весами точек в ячейке сетки, а не с индивидуальными DOM-элементами.
Каждый маркер снабжён всплывающей карточкой (popup), формируемой из HTML-фрагмента на стороне Python. Карточка содержит: дату пожара, наименование населённого пункта и района, вид объекта, причину пожара (если указана), материальный ущерб, число погибших и пострадавших, время реагирования пожарного подразделения. HTML-фрагмент экранируется функцией markupsafe.escape() до передачи в Folium, что исключает инъекцию произвольного HTML через значения полей базы данных.
Генерация карты выполняется как фоновая задача через ту же инфраструктуру JobStore, что и прочие длительные операции. При запросе страницы fire_map.html проверяется наличие актуального HTML-объекта карты в Redis (TTL 3600 с). При наличии кэша карта возвращается немедленно и встраивается в iframe. При отсутствии — запускается фоновая генерация, пользователь видит индикатор прогресса, и после завершения задачи iframe обновляется через fetch() без перезагрузки страницы. Такая схема обеспечивает приемлемое время первого отображения страницы даже при ресурсоёмкой генерации карты с DBSCAN-слоем.

4.6 Результаты разработки и выводы по главе
4.6.1 Описание реализованного программного комплекса
В рамках четвёртой главы разработан и протестирован сервис интеллектуального анализа данных, предназначенный для поддержки принятия решений в области пожарной безопасности сельских территорий. Сервис представляет собой веб-приложение с серверной частью на Python/FastAPI, реляционным хранилищем PostgreSQL 15, кэшем Redis 7 и браузерным интерфейсом на основе Jinja2 и Bootstrap 5.
Функционально сервис разделён на два независимых уровня. Первый уровень — ETL-подсистема — обеспечивает приём файлов в форматах XLSX, XLS и CSV, автоматическое сопоставление столбцов с целевой схемой посредством нечёткого сравнения строк (fuzzywuzzy, порог 85), нормализацию топонимов (unidecode, regex), приведение дат к единому формату, валидацию с направлением некорректных записей в карантин и запись нормализованных данных в таблицу cleaned_fires через upsert-операцию. Каждая операция импорта журналируется в etl_log с детальной статистикой обработки.
Второй уровень — аналитический комплекс — включает шесть модулей. Модуль информационной панели формирует агрегированные KPI и три типа интерактивных диаграмм (динамика, рейтинг районов, распределение по видам объектов) с кэшированием результатов на 300 секунд. Модуль сценарного прогноза строит GLM Пуассона на месячном временном ряду с лаговыми и гармоническими признаками, оценивает качество методом скользящего обучения и формирует три сценария (оптимистический, базовый, пессимистический) на горизонты 30, 60 и 90 суток посредством параметрического бутстрепа (1 000 итераций). Модуль машинного обучения обучает GradientBoostingRegressor с подбором гиперпараметров через GridSearchCV и TimeSeriesSplit, вычисляет метрики MAE, RMSE, R², строит профиль важности признаков и сохраняет модель на диск через joblib. Модуль кластеризации разбивает районы на группы методом k-средних с автоматическим выбором числа кластеров по методу локтя и коэффициенту силуэта. Модуль анализа проблемных точек ранжирует населённые пункты по нормированному индексу риска [0; 100] и визуализирует результаты тепловой картой Folium HeatMap. Модуль интерактивной карты формирует многослойный HTML-документ Folium/Leaflet с маркерами пожаров, KDE-тепловой картой, DBSCAN-кластерами очагов и приоритетными зонами риска.

4.6.3 Выводы по главе
В четвёртой главе описана полная реализация сервиса интеллектуального анализа данных о пожарах: от подготовки среды разработки до тестирования готового комплекса. Разработанный сервис охватывает весь цикл работы с данными: загрузку и нормализацию разнородных источников, хранение в единой аналитической таблице, вычисление прогнозных и классификационных моделей, визуализацию результатов в браузерном интерфейсе.
К ключевым техническим решениям, принятым в ходе разработки, относятся следующие. Разделение хранилища на четыре уровня (сырые данные, карантин, журнал ETL, нормализованная таблица) обеспечивает прослеживаемость происхождения каждой записи и возможность повторной обработки при изменении правил нормализации. Использование нечёткого сопоставления строк для автоопределения маппинга решает практическую проблему несовместимости форматов ведомственной отчётности без ручной настройки для каждого источника. Применение асинхронной ASGI-модели с ThreadPoolExecutor и потокобезопасным хранилищем задач позволяет обслуживать интерактивные запросы одновременно с выполнением длительных вычислительных операций. Трёхуровневая система кэширования (Redis TTL, LRU in-process, дисковый кэш joblib) дифференцирует стратегии хранения по типу и объёму данных, обеспечивая время отклика на аналитических страницах менее 20 мс при повторных обращениях. Использование параметрического бутстрепа для формирования сценариев прогноза даёт лицу, принимающему решение, не только точечную оценку, но и количественно выраженную неопределённость, что соответствует требованиям к системам поддержки принятия решений.
Результаты тестирования подтвердили корректность реализации всех компонентов: ETL-подсистема обработала три разнородных файла общим объёмом 18 272 записей с точным соблюдением правил валидации и карантина; аналитические модули продемонстрировали показатели качества выше базового прогноза (seasonal naive); все пять выявленных дефектов устранены. Разработанный комплекс соответствует всем восьми функциональным и нефункциональным требованиям технического задания.
Материалы данной главы являются основой для формулировки практических выводов о применимости разработанного сервиса в деятельности противопожарных служб, которые представлены в заключении диссертации. Достигнутые показатели точности прогнозирования, выявленные территориальные закономерности и реализованный инструментарий визуализации составляют совокупный результат, позволяющий оценить научную и практическую значимость проведённого исследования.
